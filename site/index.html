A2 two-head: 3-conv-block CNN, 100K params → command head (11-way, global max) + slot head (6 per-class sub-heads, 43 values, reads the tail cells where the slot word lives). 3.0 s window, right-aligned.

POST /device/command → light / timer / thermostat / music / dialer

Why a separate gate, not a 3rd head on the VCM? The wake question runs 100% of the time, the intent question only after a wake — merging them forces the full VCM backbone to run on every chunk all day, deleting the power-saving split. Also: different input windows (sliding vs post-wake), different data scale (1–2k vs 13.8k), different failure budgets (false wake = cheap, false intent = annoying). Full rationale: Design Whys ↓
Why plain CNN, not CRNN? After 3 maxpools the time axis is 6 frames — no sequence left to read. Output is one label, not a sequence (CRNN/CTC exists for ASR). RNNs are sequential compute — the worst workload for the Pi's ARM cores. Google's own keyword-spotting model is the same architecture class. Documented fallback: a temporal variant for the slot head (position-sensitive), not the intent head.
Why ONNX on the Pi? PyTorch is a ~2GB install with slow ARM kernels; ONNX Runtime is ~50MB with optimized ARM kernels — real on a 64GB SD. Same .onnx file runs on the Pi, dev machine, and web. TensorRT rejected: no ARM64 build.
